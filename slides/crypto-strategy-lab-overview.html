Crypto Strategy Lab

Platform for Analyzing, Combining & Evaluating Crypto Trading Strategies

Architecture Quality Over Trading Profitability
02 / 08

What Is This Project?

  • Ingests real-time market data from Binance, displays multi-timeframe candlestick charts
  • Composes individual strategies into composite strategies, backtests them on historical data
  • Ranks them on a leaderboard, runs a continuous search loop to discover better combinations
  • Collects news & runs ML sentiment analysis as an extensible strategy plugin
Core thesis: The grading criterion is not whether MA+RSI makes money. It's whether new strategies, new search algorithms, new data providers, and new sentiment models can be added with minimal code changes.
"Today the system has MA+RSI. Tomorrow someone adds SMC, Wyckoff, Sentiment, or a completely new strategy — and the old architecture still works. THAT is Software Architecture."
03 / 08

Business Use Cases — Core System

1. Realtime Market Data

Binance → Adapter → Event Bus → WebSocket → Frontend. Historical + real-time candles. Max 4 simultaneous timeframes.

2. Strategy Plugin System

MA, RSI, Bollinger, Support/Resistance. Add new strategy = 1 file + 1 register() call. Zero changes to backtester/evaluator/leaderboard.

3. Composite Strategy

Combine N strategies. Majority Vote or Weighted Score. MA→BUY, RSI→SELL, SR→BUY = score-based decision.

4. Backtesting Engine

Replay historical candles → simulate trades → compute Return, Win Rate, Max Drawdown, Sharpe Ratio.

04 / 08

Business Use Cases — Platform Features

5. Strategy Search Loop

Generate → Backtest → Evaluate → Rank → Leaderboard → Generate next. Bounded stop condition — no unbounded while(true).

6. Leaderboard

Top-K ranking, sortable by Return, Win Rate, MDD. Updates in real-time via WebSocket events — no page refresh needed.

7. News & Sentiment

Crawl news → store → ML sentiment analysis (Python FastAPI) → SentimentStrategy plugs into registry. If news service down → returns HOLD (graceful degradation).

What You Build — Hoàng

  • BinanceAdapter — implements IMarketDataAdapter. REST historical klines + WebSocket real-time streams. All Binance JSON parsing stays inside the adapter.
  • MarketDataService — caching (LRU + TTL), subscription deduplication (multiple clients share one Binance stream), serves normalized Candle entity.
  • MarketDataGateway — NestJS WebSocket Gateway relaying live candles + connection status to frontend clients.
  • Shared types & interfaces in libs/shared — ICandle, ISignal, IStrategy, IMarketDataAdapter. All other modules depend on these.
  • Prisma schema + migrations — Candle, TradingPair, Strategy, Backtest, NewsArticle, LeaderboardEntry, SearchLoopRun tables.
  • Frontend charts — CandlestickChart (lightweight-charts), MultiTimeframeGrid (4 charts), ChartOverlay (MA/Bollinger/SR + buy/sell markers).
  • Auto-Reconnect — bounded exponential backoff (1s, 4s, 16s, max 3 attempts), gap recovery via REST, frontend status notifications.
  • Knowledge Base — INDEX, CONSTITUTION, ARCHITECTURE, ADRs 0001–0007, market-data.yaml contract, market-data.md, patterns catalog.
08 / 08

Why It Matters — Your Purpose

  • Data Spine — every module consumes your Candle entity and shared interfaces. Without your adapter pattern, the frontend would be coupled to Binance's JSON format forever.
  • Architect — you set the module boundaries, constitution principles, and coding standards. The team works within your boundaries.
  • Adapter Pattern (ADR-0004) — answers spec §40.3: "Add OKX data source = 1 new class, frontend unchanged." This is your extensibility proof for the interview.
  • Modular Monolith (ADR-0002) — answers §32.2 (Scalability): one process, clean boundaries, extraction path to microservices preserved.
  • Auto-Reconnect (ADR-0007) — answers §32.4 (Reliability): no lost candles, bounded retry, user always knows connection state.
In the interview: "I designed the system as a modular monolith. Each NestJS module has clean boundaries. I implemented the Binance Adapter — if you want to add OKX, you create one class implementing IMarketDataAdapter. The frontend and strategy engine never know which data source is active. I also defined the shared type system that all modules depend on."
